# Architecture Decision Records

## ADR-001 — Adopt spec-driven harness
**Status:** Accepted
**Context:** Project had no code yet, only planning docs (`Roadmap.md`, `Worklist.md`, `README.md`). Old generic `.specs/` scaffold was removed. Needed a discipline so any agent/dev touching the repo works from specs, not ad-hoc.
**Decision:** `AGENTS.md` (short, YAML, no prose) mandates loading `.specs/SPECS.md`, `.specs/SKILLS.md`, `.specs/ADRS.md` before any task, and requires `CHANGELOG.md` update every session. Specs live one file per feature/module at `.specs/{feature}-{module}-spec.md`. Skills indexed in `.specs/SKILLS.md`, files under `.specs/skills/`.
**Consequences:** No code change happens without a matching spec entry. Slightly more overhead per task, but traceable decisions and no drift between docs and code.

## ADR-002 — Build order: Mitosis/components first, backend later
**Status:** Accepted
**Context:** `Worklist.md` originally sequenced work Backend-first (BK-001 Postgres schema before anything else). All later tasks (CLI, Studio, Compiler, QA) depend on that schema existing.
**Decision:** Invert the order. Start with the Mitosis compiler and component AST pipeline; build the rest of the system (backend, CLI, Studio) around the components produced this way.
**Consequences:** Backend/DB work is deferred — `Worklist.md` dependency chain (BK-* → CLI-* / ST-* → CP-* → QA-*) no longer reflects actual execution order and needs revisiting once backend work starts.

## ADR-004 — Pilot component AST authored by hand
**Status:** Accepted
**Context:** Studio (ST-001/ST-002) doesn't exist yet, so there's no visual builder to produce a component AST.
**Decision:** The pilot component's AST is a hand-written JSON file following `.specs/ast-component-spec.md`. The Mitosis compiler pipeline consumes this JSON the same way it will later consume Studio-generated ASTs. Which component becomes the pilot (Button, etc.) is decided at implementation time, not fixed now.
**Consequences:** AST spec must be generic enough to support both hand-authored JSON now and Studio output later — no Studio-specific shortcuts in the format.

## ADR-005 — Mandatory component quality gate + 3-layer QA strategy
**Status:** Accepted
**Context:** Nothing enforced semantic HTML5, accessibility, performance, or animation discipline on components coming out of the compiler. Without a written gate, quality depends on whoever happens to be building a component that day.
**Decision:** Every component must satisfy `.specs/component-quality-spec.md` (semantic HTML5, WCAG 2.1 AA, mandatory multi-modal access — keyboard/voice/screen-reader, a documented performance budget, animation via theme tokens only). Verification follows a 3-layer strategy documented in `.specs/component-qa-strategy-spec.md`: Playwright+axe-core (automated baseline, `Worklist.md` QA-001) → Storybook (playground + a11y/interaction addons, QA-002) → Cypress (real browser UI/UX flows, QA-003). Only the contracts are written this round — enforcement today is manual, via `.specs/skills/component-quality-checklist.md`; automation lands when there are enough real components to justify it.
**Consequences:** Every future component has a fixed bar to check against instead of an ad-hoc one. The 3 QA layers aren't implemented yet — `Worklist.md` tracks that as separate, still-pending tasks (QA-001/002/003).

## ADR-006 — AST v1: state, events, conditionals, loops + static quality-gate enforcement
**Status:** Accepted
**Context:** AST v0 only covered props → static attributes/text — enough to prove the Mitosis pipeline works, not enough to describe a real component (no state, no interaction, no conditional/repeated content). Also, ADR-005's quality gate defined rules that are mechanically checkable at the AST level (semantic tag for events, accessible name, `img alt`, `tabindex`) but nothing enforced them yet.
**Decision:** Extend the AST (`ast-component-spec.md`) additively with `state`, event attributes (`{ on: expr }`), conditional nodes (`{ show: {...} }`), and loop nodes (`{ for: {...} }`) — mapped 1:1 to Mitosis's internal conventions, confirmed by manual testing against `@builder.io/mitosis@0.14.0`: `state` field shape comes from how `useStore` (not `useState`) parses; events use `bindingType: 'function'`; conditionals/loops use the built-in `Show`/`For` node names. At the same time, `validate.ts` starts enforcing the AST-level quality-gate rules from `component-quality-spec.md` — a violation aborts compilation, same severity as a structurally invalid AST.
**Consequences:** Every v0 AST stays valid (additive change). Components with state/events/conditionals/loops can now be described, but focus management around `show`/`for` remains unsolved (tracked as an open item, not retrofitted here). Quality-gate rules that need runtime inspection (`aria-live`, `prefers-reduced-motion`, focus) are still not enforced anywhere — only the statically-checkable subset is, and that gap is documented in `mitosis-compiler-spec.md`, not hidden.

## ADR-007 — QA-001 tests the compiler's HTML output, not React/Vue rendering
**Status:** Accepted
**Context:** Implementing layer 1 of the QA strategy (`component-qa-strategy-spec.md`) needs a rendered DOM to run axe-core against. Rendering the React or Vue output for real would require a bundler (esbuild/vite) and a JSX/SFC runtime just for testing — extra toolchain, extra maintenance, for a check that's fundamentally about markup/ARIA structure, not framework behavior.
**Decision:** QA-001 runs Playwright + axe-core against the framework-agnostic HTML Mitosis's `componentToHtml()` already produces (the same generator used for the Astro workaround, ADR-006's precursor) — wrapped in a minimal standalone document with `<html lang>` and `<title>` (both required, confirmed by manual testing: axe-core flags their absence at the document level, which is noise unrelated to the component). `compile.ts` gains a `qa-html` output alongside `mitosis`/`react`/`vue`/`astro`.
**Consequences:** Catches real structural/ARIA violations in the markup the compiler actually emits, no bundler needed. Doesn't catch framework-specific rendering bugs (a React-only regression, a Vue directive typo) — that gap is explicit, not hidden, and is where Layer 2 (Storybook, `QA-002`) is expected to eventually add coverage.

## ADR-008 — WCAG target bumped to 2.2 AA, with an explicit per-criterion scope map
**Status:** Accepted
**Context:** Asked to guarantee coverage of all 24 AA-exclusive success criteria (WCAG 2.1 + 2.2 combined). Not all 24 apply at the same layer — several are site-level (consistent navigation, multiple ways to find a page), flow-level (error prevention on legal/financial submission, accessible authentication), or media-content-level (live captions, audio description). A single compiled component's AST structurally cannot satisfy those; claiming otherwise would be false confidence, not a real quality gate.
**Decision:** Move the stated target from WCAG 2.1 AA to **2.2 AA** (a strict superset — 4 new criteria, nothing removed) and add a full 24-criteria mapping table to `component-quality-spec.md`, each row tagged with its real applicable layer (component/AST-static, component/axe-automated, app-level-out-of-scope, or tracked-gap-pending-AST-feature). Implemented what's cheaply automatable this round: axe-core's `wcag22aa` tag (pulls in `target-size`, SC 2.5.8) added to the QA-001 runner, plus a new reflow check (SC 1.4.10 — 320px viewport, no forced horizontal scroll).
**Consequences:** Nothing is silently dropped — every one of the 24 criteria has an explicit status (enforced today, tracked for later, or genuinely out of scope for a component compiler). Contrast-related rules (1.4.3, 1.4.11) run today via axe but won't catch anything meaningful until real color tokens exist (Tailwind classes aren't resolved to actual colors yet) — that's a known limitation, not a false pass. Site/app-level criteria (2.4.5, 3.2.3, 3.2.4, 3.3.4, 3.4.1) are explicitly the Studio/backend's responsibility, not the compiler's — revisit there, not here.

## ADR-009 — Static output (Astro, `qa-html`) switches from `componentToHtml` to `componentToTemplate`, for SEO/GEO
**Status:** Accepted
**Context:** Asked to make components "SEO perfect and GEO perfect." Found a real problem in the existing static output: `componentToHtml()` renders empty `data-el` placeholder elements whose text gets filled in by an injected `<script>` after the page loads. Search crawlers that skip JS execution — and effectively all LLM/AI-answer-engine crawlers today — see empty markup. This defeats the entire point of a semantic, crawlable static output, and specifically undermines Astro's own value proposition (static-first, minimal JS).
**Decision:** Switch the Astro and `qa-html` targets to `componentToTemplate()` instead. Confirmed by manual testing that it correctly handles `Show`/`For`/`state` (ternary, `.map().join()`, baked initial values respectively) and produces genuinely static markup with real text. Because `componentToTemplate` is a code generator (returns function *source*, not a callable value), `render-static.ts` transforms the generated source (`export default function` → `module.exports =`) and executes it via a throwaway `require()`d temp file, called with example prop values — a new optional `example` field on `ComponentProp` (`ast-component-spec.md`), falling back to an empty/zero/false value per type when absent. Also added a `validate.ts` rule: every `a` node needs `href` (a link with no `href` doesn't exist to any crawler). Structured data (schema.org JSON-LD) is documented as a tracked v2 feature, not implemented this round.
**Consequences:** Astro/`qa-html` output now has real, crawlable text and links — the actual goal. Trade-off, explicit not hidden: this static render has zero client-side interactivity (a button's `onClick` is inert in this output) — React/Vue remain the interactive targets; real Astro island-based interactivity is a later concern. The `example`-value mechanism means components without a thoughtfully chosen example still produce technically-valid but content-empty static output — a spec requirement, not something code can force.

## ADR-010 — Beaconray Theme: Royal Cyan palette + Atkinson Hyperlegible, CSS-agnostic token mechanism, mandatory responsiveness
**Status:** Accepted
**Context:** `component-quality-spec.md` rule 5 required animation tokens but the token system itself was never designed. Asked to broaden scope to a full theme (color/typography/spacing/animation, generically "anything CSS"), reject any Tailwind/CSS-lib coupling in the core, supply the platform's official default palette (Royal Cyan: `#056583`/`#37849c`/`#69a3b5`/`#9bc1cd`/`#cde0e6`) and font (Atkinson Hyperlegible, chosen after rejecting Inter as too generic), and make 100% responsiveness mandatory for every component.
**Decision:** `.specs/theme-spec.md` defines the Beaconray Theme: token catalog (color, typography, spacing/sizing, animation, focus-visibility, responsiveness) as plain CSS custom properties (`--br-*`) in `compiler/theme/tokens.css`, consumed via `var()` in the AST's existing `style` attribute — no schema change, no framework dependency. Royal Cyan's role assignments and dark-mode substitutions come from actually computing WCAG contrast ratios (relative-luminance formula, via `node`), not assumption — e.g. `#056583` passes 6.57:1 as both text-on-white and button-background-with-white-text, but is too weak in dark mode (3.01:1) so `#69a3b5` (7.08:1) takes over as dark-mode primary; adjacent Royal Cyan steps have too little mutual contrast (~1.4–1.5:1) to pair as border/surface. This also closes WCAG SC 2.4.7 (Focus Visible, previously "tracked — add when style tokens land" in the ADR-008 mapping table) via a global `:focus-visible` rule using a verified-contrast focus-ring token. `validate.ts` gains static enforcement for raw color, raw time, and fixed-pixel width/height in `style`.
**Consequences:** Real, verified-accessible default colors exist now, which is also what finally makes axe-core's contrast rules (1.4.3, 1.4.11) catch something meaningful instead of running against contentless markup (ADR-008's noted limitation starts closing). Font-size/spacing enforcement remains undone — a reliable check needs a real CSS parser, not regex, and is documented as a gap rather than faked. The palette is intentionally small (5 steps) — a fuller brand palette is Studio's visual theme editor's job (Fase 2), not this spec's. The token-file architecture (swap values, never touch component code) is deliberately what would make themes shareable/publishable later (`PLAT-001`, tracked, not built).

## ADR-011 — aria-live heuristic, focus-on-show via `onUpdate`, structured data (SEO-002)
**Status:** Accepted
**Context:** Three items had been deferred across multiple rounds: `aria-live` for dynamic content not directly caused by the user's action on that element (component-quality-spec.md rule 3), focus management around `Show`/`For` (ADR-006's open item), and structured data (schema.org, tracked since the SEO/GEO round). Before committing to an approach for focus management, checked whether Mitosis actually supports a dependency-tracked effect (not just `onMount`, which only fires once regardless of a nested conditional's toggles) — confirmed via manual testing that `hooks.onUpdate` with a `deps` array exists and compiles to `useEffect(() => {...}, [deps])` in React and a `computed`+`watch({ immediate: true })` pair in Vue, both of which correctly re-fire on every transition, not just initial mount.
**Decision:** (1) `aria-live` enforcement in `validate.ts`: a state-bound node needs `aria-live` (self or ancestor) unless it's inside (itself or a descendant of) an element with any event binding — a deliberate heuristic (exempts by "any event nearby," not by tracing which exact state variable that event modifies, which would need real JS expression parsing). (2) `show.focusOnShow` (`ast-component-spec.md` v1.2): generates a `ref` + `tabIndex: -1` on the Show block's first child and an `onUpdate` hook with the show condition as its dependency, calling `.focus()` — verified end-to-end, compiles correctly to both React and Vue. (3) `schema` (v1.2): optional JSON-LD object on `ComponentAst`, validated to require `@context`/`@type`, emitted as a `<script type="application/ld+json">` in the static output.
**Consequences:** `aria-live` enforcement is a heuristic, not perfect data-flow analysis — it can under-flag in unusual cases (an event far away in the tree that happens to modify the same state var as a display elsewhere would incorrectly exempt that display if they share a common event-bearing ancestor... actually this doesn't happen since exemption requires being a *descendant* of the event-bearing node, not just a sibling — the real limitation is only that it doesn't verify the event actually modifies the *same* state variable being displayed, just that *some* event exists nearby). Focus management for `For` (list-item removal) remains explicitly unsolved — a real gap, tracked, revisited only once there's an actual list component to test against rather than solved speculatively.

## ADR-012 — Component catalog v1 (34 components), base-vs-complex is architectural not commercial
**Status:** Accepted
**Context:** Needed to fix which components Beaconray actually builds before building any of them, so the platform can eventually construct a whole site/app/system from its own catalog alone. Proposed 47 candidates across 3 tiers (structural, interactive, complex); the user screened every one against a single question — "does it have real behavior beyond what a dev would write in two minutes?" — cutting anything that was just a styled wrapper (`Section`, `Panel`, `AppShell`, standalone `Grid`/`Checkbox`/`Radio`/`Switch`/`Select`/`Slider`) and merging near-duplicates (`Checkbox`+`Radio`+`Switch` → `Switcher`; `Select`+`Combobox` → `Dropdown`; `Sidebar` → an orientation prop on `Navbar`; `Sheet` → a position prop on `Drawer`).
**Decision:** `.specs/component-catalog-spec.md` fixes the v1 list at 34 components across 3 layers (5 structural, 18 interactive, 11 complex) plus per-category pattern conventions (form control, overlay, structural, navigation) that reference existing specs rather than inventing new rules. The base-vs-complex split is kept for architectural reasons (complex components consume base components' AST/API, not duplicate logic) — but is explicitly **not** the monetization boundary. The user's first instinct was to tie pricing to this split; reconsidered mid-session in favor of usage-based pricing per project (one free trial project, pay to use across more than one) — the two decisions are deliberately kept separate so neither gets silently conflated with the other later.
**Consequences:** Every future component-building session has a fixed list to build against instead of re-deriving one. Notable redefinitions to remember: `Input` uses a floating-label pattern (not a plain field), `Dropdown` requires optional search + async paginated infinite scroll (not a plain `<select>`), `Popover` is more generic than `Modal` (no mandatory header/footer) and `Toast` is just `Popover` + a timer, `Tooltip` must swap content in place rather than close/reopen on fast refocus. `Date Picker` and `Kanban`'s exact designs remain open — explicitly not solved here.

## ADR-016 — Backend stack: bare Symfony skeleton, AWS SDK direct for MinIO, League OAuth2, Redis Messenger, Opis JSON Schema
**Status:** Accepted
**Context:** `BK-001`..`BK-005` need concrete library choices Symfony itself doesn't ship: an API layer, an S3-compatible client for MinIO with presigned-URL support, an OAuth2 *server* (Symfony core has no OAuth2 server implementation), a Redis transport for Messenger, and a JSON Schema validator. Researched current (2026) options for each rather than assuming.
**Decision:**
- **`symfony/skeleton` + `composer require api`** (Flex recipe installs `api-platform/core`), not the full `api-platform/api-platform` distribution — the latter bundles Caddy/Mercure/PWA-admin scaffolding not needed at this stage (same pacing principle as ADR-005: don't install infra ahead of actual need).
- **`aws/aws-sdk-php`'s `S3Client` directly** for MinIO, not `league/flysystem-aws-s3-v3`/`symfony/flysystem-bundle` — presigned URL generation (the actual `BK-003` requirement) has no first-class support in the Flysystem bundle (open, unresolved upstream feature request, confirmed via research); `S3Client::createPresignedRequest()` signs with SigV4 (HMAC-SHA256 under the hood), satisfying the Worklist's requirement with no extra crypto code.
- **`thephpleague/oauth2-server-bundle`** as the OAuth2 server for CLI auth (`npx beaconray login`) — the standard, actively-maintained Symfony-ecosystem choice, since Symfony Security only handles authentication/authorization, not issuing OAuth2 tokens itself.
- **`symfony/redis-messenger`** as the Messenger Redis transport — the official Symfony bridge package, not a third-party one.
- **`opis/json-schema`** for `BK-002`'s AST validation — actively maintained, supports current JSON Schema drafts, chosen over the older/slower-moving `justinrainbow/json-schema`.
- **`CompileComponentJob` (`BK-004`) shells out to the existing Node compiler via `Symfony\Component\Process\Process`**, reusing `compiler/src/compile.ts`'s already-stable `[ok]`/`[fail]`/`[abort]` stdout/stderr contract verbatim — no HTTP microservice, no changes needed on the Node side. A microservice split is not justified at this stage (ADR-005 pacing).
**Consequences:** Every backend dependency has a stated reason instead of being picked by default/familiarity. If `BK-003`'s presigned-URL needs change shape later, revisit the Flysystem-bundle decision (the upstream gap may close). `SYMFONY_GUIDE.md` (backend) documents each package's role file-by-file as the code lands.

## ADR-017 — Backend structure: flat idiomatic Symfony/API Platform, no domain modules
**Status:** Accepted
**Context:** An initial proposal structured the backend as domain modules (`Component/`, `Identity/`, `Artifact/`, `Compilation/`, each with `Domain/Application/Infrastructure/UI`) — a hexagonal/DDD-flavored layering. The user explicitly rejected this: "o DDD foi apenas uma sugestão [não uma decisão]... eu quero seguir a comunidade [Symfony]." Researched Symfony's own official best practices and current API Platform convention rather than defaulting to the DDD proposal.
**Decision:** Backend code lives flat under `src/`, organized **by technical kind, not by domain**: `Entity/`, `Repository/` (Doctrine's own `ServiceEntityRepository` — already the repository pattern, no custom interface layered on top), `ApiResource/` (DTO-as-Resource, only where the public API contract must diverge from the Doctrine entity — API Platform's own recommended decoupling mechanism), `State/Provider/` + `State/Processor/` (custom, only where API Platform's built-in Doctrine provider/processor doesn't fit — e.g. the `/v1/cli/*` endpoints), `MessageHandler/`, `Validator/`, `Security/Voter/`, `Storage/`. No top-level domain/module folders. Generic `Service/` is deliberately avoided (a well-documented anti-pattern in larger Symfony projects — becomes a dumping ground) in favor of purpose-named folders.
**Consequences:** Matches how the Symfony/API Platform community actually structures projects (confirmed via `symfony.com/doc/current/best_practices.html` and `api-platform.com/docs/core/{state-providers,state-processors,dto}`) rather than importing an external architectural style. Entities renamed during this pass: `Component` → `Library` (the catalog item), `Compilation` dropped as a concept — it's just `MessageHandler/CompileVersionHandler.php`, not a domain. Decoupling (State Provider/Processor, DTO-as-Resource) is applied selectively, only where the public contract genuinely needs to diverge from the persisted shape — not blanket-applied everywhere.

## ADR-018 — Personal dev-infra stack, production via Kubernetes
**Status:** Accepted
**Context:** Local development needs Postgres, Redis, MinIO, and routing for a `.test` domain (`beaconray.test`). This project is kept fully agnostic of any external organization or other codebase — infra decisions here are evaluated on technical merit alone, not by mirroring anything specific.
**Decision:** A separate, reusable local dev-infra stack (own repository, `/home/guilherme/pessoal/dev-infra` — outside this repo, shared across personal projects) provides Postgres (`pgvector/pgvector:pg16` image — bundles pgvector plus standard Postgres contrib modules including `pg_trgm` for trigram-based fuzzy search, both enabled via init SQL), Redis, MinIO, and a file-provider-based reverse proxy routing by host. No dev/prod docker-compose split — **production deploys via Kubernetes**, not Swarm or compose; the local stack's docker-compose is dev-only.
**Consequences:** `app/backend`'s own `docker-compose.yml` only joins the external dev-infra network — it does not declare its own Postgres/Redis/MinIO containers. Kubernetes manifests for production are a separate, later effort (tracked, not built this round — `Roadmap.md`/`Worklist.md` Fase E).
